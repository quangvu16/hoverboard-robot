Hoverboard robot

A hoverboard that maps the room and drives itself there. The motors, mainboard and battery come from a scrapped self-balancing hoverboard. An ESP32 reads the LiDAR, IMU and sonars, drives the mainboard, and sends everything over Wi-Fi to a ROS 2 Humble PC. That PC runs SLAM, Nav2 and RViz.

(01)Idea

Why a hoverboard, and why split the brain in two

The robot started as a small differential-drive base built around an ESP32 that spoke JSON over TCP (esp_tcp_server_node, port 9000). That base is still supported. The project then moved to a hoverboard chassis, because the hub motors, battery and FOC mainboard come in one cheap package with plenty of torque.

The design keeps the work split cleanly. Anything that must be on time and must keep working with Wi-Fi down runs on the ESP32: wheel speed control, sonar reflexes, lights and the IMU fusion. Anything that needs real compute runs on the PC under ROS 2: maps, plans, costmaps and the EKF.

On the mainboard

The motor's own FOC control loop. It zeroes its command after 0.8 s of serial silence.

On the ESP32

A PI speed loop per wheel, the LiDAR decoder, three HC-SR04 reflexes, turn and stop lights, a buzzer and MPU9250 fusion. It knows RPM and ticks, never metres.

On the PC

All geometry lives in metres in one YAML file. The PC also runs odometry, TF, the EKF, Cartographer or slam_toolbox, Nav2 and RViz.

Mainboard wiring

Connect three wires only: GND, TX→GPIO26 and RX←GPIO27. Leave the mainboard's VCC pin open. It can carry 15 V and cannot power an ESP32. USART2 is 3.3 V logic and is not 5 V tolerant.

(03)Firmware

Two firmwares and three wire formats

Mainboard

hoverboard-firmware-hack-FOC, built with VARIANT_USART. The board here runs the stock upstream build, which sends 18-byte feedback with no wheel counters. The ESP32's own speed loop (HB_SPEED_LOOP_ON 1) holds the RPM.

ESP32

~/Arduino/ldrobot_ld14p_esp32_mpu9250_ros uses only the ESP32 core, with no third-party libraries. The earlier BNO055 variant ldrobot_ld14p_esp32_ros is kept because its HOVERBOARD.md has the full build guide.

DatagramPortDirectionContents
LDS1UDP 9900ESP32 → PCmagic, u16 count, u32 scan id, then count × u16 ranges in mm, little-endian
HBT1UDP 9902ESP32 → PCAccumulated ticks (so a lost datagram costs nothing), RPM, battery, sonars, lights. Bytes 52–73 carry the IMU: 74 bytes in total.
HBC1UDP 9901PC → ESP32Wheel RPM targets; flag bit1 drives the buzzer
IMU note

The MPU9250 runs gyro and accelerometer fusion on the ESP32, with no compass, because the hub-motor magnets corrupt it. It reports in the BNO055's units, so the bridge works with either chip. The bridge holds back /imu/data until calibration reports gyro 3. Keep the robot still for about 2 s after power-on so it can learn the gyro bias.

Odometry and TF

  • With ekf:=true (the default), the EKF owns odom → base_footprint and publishes /odom/filtered, which Nav2 and Cartographer read.
  • With ekf:=false, the bridge publishes raw wheel odometry and TF.
  • With wheel_odom:=false on both launches, Cartographer uses only the LiDAR and IMU and publishes /odom/cartographer.

Second workspace

~/slam_toolbox_ws holds slam_toolbox v2.6.9, retuned for this robot: max range 6 m when mapping and 3.5 m when localizing, with a 1 s map update. These changes are uncommitted, so never reset that tree.

(05)Install

From a blank Ubuntu 22.04 to a built workspace

  1. ROS 2 Humble and the stack's packages

    Nav2, Cartographer, robot_localization, CycloneDDS and the teleop tools.

    shell
    sudo apt install ros-humble-desktop ros-humble-navigation2 ros-humble-nav2-bringup \
  ros-humble-cartographer-ros ros-humble-robot-localization \
  ros-humble-rmw-cyclonedds-cpp ros-humble-teleop-twist-keyboard python3-colcon-common-extensions

  2. Shell environment

    Source local_setup.bash, not setup.bash. The latter replays the prefix chain recorded at build time and can pull in stale overlays.

    ~/.bashrc
    source /opt/ros/humble/setup.bash
source ~/slam_toolbox_ws/install/local_setup.bash
source ~/robot_ws/install/local_setup.bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp

  3. Build both overlays

    Builds are plain colcon build, without --symlink-install. Config is read from the install space, so rebuild a package after editing its YAML.

    shell
    cd ~/slam_toolbox_ws && colcon build
cd ~/robot_ws && colcon build
source ~/robot_ws/install/local_setup.bash
# one package after an edit
colcon build --packages-select esp_tcp_server hoverboard_base_node

  4. Flash the mainboard

    Build hoverboard-firmware-hack-FOC with VARIANT_USART. If you change its N_MOT_MAX, mixer coefficients or inverts, change the matching HB_MB_* constants in the ESP32's config.h too.

  5. Flash the ESP32

    Set your Wi-Fi SSID and password in config.h. Upload at 115200 baud: faster speeds fail on this board. A flash id of ff/ffff means a wiring or hardware fault, not a software one.

    shell
    S=~/Arduino/ldrobot_ld14p_esp32_mpu9250_ros
arduino-cli compile --fqbn esp32:esp32:esp32 $S
arduino-cli upload  --fqbn esp32:esp32:esp32:UploadSpeed=115200 -p /dev/ttyUSB0 $S
(06)Deploy

Bring the robot up and prove each link

  1. Open the network

    The PC and ESP32 must be on the same LAN. On a VM, use a bridged adapter, not NAT.

    shell
    sudo ufw allow 9900/udp && sudo ufw allow 9901/udp && sudo ufw allow 9902/udp

  2. Power on and check the serial boot log

    At 115200 baud you should see the Wi-Fi address, then LiDAR: sending 360-bin scans and a hoverboard: line with battery voltage. no feedback on GPIO26 means the mainboard isn't talking: TX/RX swapped, no common ground, or the power button wasn't pressed.

  3. Start bringup (one stack at a time)

    Before launching, make sure no other bringup or Nav2 is running. Duplicate bridges fight over UDP 9902.

    shell
    ros2 launch robot_bringup robot_bringup.launch.py              # hoverboard + EKF (default)
ros2 launch robot_bringup robot_bringup.launch.py ekf:=false   # raw wheel odometry
ros2 launch robot_bringup robot_bringup.launch.py base:=esp_tcp # original small base

  4. Verify every link

    shell
    ros2 topic echo /hoverboard/link_status   # esp:up mainboard:up …
ros2 topic hz /scan                       # ~6 Hz
ros2 topic hz /odom                       # ~50 Hz
ros2 topic echo --once /imu/calib_status  # want: gyro 3

  5. First drive, on blocks

    Lift the wheels off the ground first: a hoverboard has the torque to throw the chassis. Fix wheel swaps and inverts in the ESP32's config.h, never on the ROS side.

    shell
    ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.1}}'   # both forward
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist '{angular: {z: 0.5}}'  # turn left

  6. Calibrate once the sensors are mounted

    Check the scan orientation first, then the wheel track. The tools are in ~/robot_ws/tools.

    shell
    python3 ~/robot_ws/tools/lidar_mirror_test.py        # mirrored? rotated? turning with the robot?
python3 ~/robot_ws/tools/calib_wheel_separation.py   # odom yaw vs Cartographer yaw

(07)Autostart

Start the robot side at boot with systemd

A systemd service runs the same robot_bringup.launch.py as a terminal does, but it starts when the PC boots, with nobody logged in. It also restarts after a crash and writes its output to the system journal. It covers only the robot side: the bridge, LiDAR receiver, URDF and EKF. Mapping, Nav2 and RViz stay manual, because you choose a map and need a screen for them.

Proposed, not yet installed

These files aren't installed on the robot PC yet. They were checked on 11 Oct 2026: systemd-analyze verify passes. The script also started all five nodes in an isolated ROS domain and stopped them cleanly on SIGINT.

  1. Add the start script

    It sets up the same environment as ~/.bashrc, which systemd doesn't read. It sources local_setup.bash, never setup.bash.

    shell
    cat > ~/robot_ws/tools/robot_bringup.sh <<'EOF'
#!/usr/bin/env bash
# Started by robot-bringup.service. Same environment as ~/.bashrc:
# local_setup.bash, never setup.bash.
set -e
source /opt/ros/humble/setup.bash
source "$HOME/slam_toolbox_ws/install/local_setup.bash"
source "$HOME/robot_ws/install/local_setup.bash"
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
unset ROS_LOCALHOST_ONLY
# Extra launch arguments come from the unit's ROBOT_ARGS (e.g. "ekf:=false").
exec ros2 launch robot_bringup robot_bringup.launch.py $ROBOT_ARGS
EOF
chmod +x ~/robot_ws/tools/robot_bringup.sh

  2. Add the service unit

    The unit waits for the network, because the bridge needs Wi-Fi. It runs as user vu so the workspaces in that home directory resolve. It stops with SIGINT, which shuts ros2 launch down cleanly, the same as Ctrl-C.

    shell
    sudo tee /etc/systemd/system/robot-bringup.service >/dev/null <<'EOF'
[Unit]
Description=Hoverboard robot bringup (bridge, LiDAR, URDF, EKF)
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=vu
Environment=ROBOT_ARGS=
ExecStart=/home/vu/robot_ws/tools/robot_bringup.sh
# ros2 launch shuts its nodes down cleanly on SIGINT, like Ctrl-C
KillSignal=SIGINT
TimeoutStopSec=20
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

  3. Enable it and start it now

    shell
    sudo systemctl daemon-reload
sudo systemctl enable --now robot-bringup
systemctl status robot-bringup        # want: active (running)
ros2 topic echo /hoverboard/link_status

  4. Pick launch arguments (optional)

    Set them in a drop-in file instead of editing the unit. For example, for LiDAR+IMU-only Cartographer:

    shell
    sudo systemctl edit robot-bringup
# in the editor, add:
[Service]
Environment=ROBOT_ARGS=wheel_odom:=false
# then
sudo systemctl restart robot-bringup

One bringup at a time

While the service runs, don't also start robot_bringup.launch.py in a terminal. Two bridges compete for UDP 9902 and both publish /odom. Stop the service first. Start mapping and Nav2 on top of the service as usual, and keep the wheel_odom mode the same on both sides.

What a restart covers

Restart=on-failure brings the launch back 5 s after it crashes or is killed. If one node dies, ros2 launch keeps running, so systemd doesn't restart anything. Check journalctl for process has died.

After a rebuild

Config is read from the install space, and a running service keeps the old executables. After colcon build, restart the service so it picks up the new build.

(08)Map & navigate

Two mapping stacks; never run both

Cartographer (recommended)

shell
# map, and navigate while mapping
ros2 launch robot_cartographer cartographer_nav.launch.py
ros2 run robot_cartographer save_map ~/m_map

# localize on the frozen map
ros2 launch robot_cartographer cartographer_nav.launch.py \
  map:=$HOME/m_map.pbstream

The 2D Pose Estimate tool in RViz works in localization mode.

slam_toolbox + Nav2

shell
# map
ros2 launch robot_bringup robot_slam.launch.py
ros2 run nav2_map_server map_saver_cli -f ~/m_map

# navigate (AMCL)
ros2 launch robot_navigation navigation2.launch.py \
  map:=$HOME/m_map.yaml
Match the modes

For LiDAR+IMU-only mapping, pass wheel_odom:=false to both bringup and cartographer_nav. If only one of them gets it, nothing publishes the odom frame and Nav2 keeps logging “Invalid frame ID "odom"”.

Driving by hand

shell
ros2 run rqt_robot_steering rqt_robot_steering        # publishes /cmd_vel_manual
ros2 run teleop_twist_keyboard teleop_twist_keyboard  # publishes /cmd_vel
ros2 launch hoverboard_ctrl joy_launch.py             # gamepad
(09)Web navigation

Send the robot somewhere from a phone or laptop

The robot_web_nav package serves a web page from the robot PC. Any browser on the same Wi-Fi can open it, with nothing to install. The page shows the map, the robot and its planned path. Click a spot and the robot drives there through Nav2. It works with both stacks, Cartographer or Nav2 + AMCL, and you choose which one at launch.

  1. Install rosbridge and build the package

    shell
    sudo apt install ros-humble-rosbridge-suite
cd ~/robot_ws && colcon build --packages-select robot_web_nav
source install/local_setup.bash
sudo ufw allow 9090/tcp && sudo ufw allow 8000/tcp   # only if ufw is enabled

  2. Launch with your choice of stack

    Bringup must already be running, either by hand or from robot-bringup.service. The launch starts rosbridge, the web server, web_nav_bridge and the chosen stack. RViz stays off, because the page replaces it.

    shell
    # Cartographer: localize on a saved map (no map:= = map while navigating)
ros2 launch robot_web_nav web_nav.launch.py stack:=cartographer map:=$HOME/m_map.pbstream

# Nav2 + AMCL on a .yaml map
ros2 launch robot_web_nav web_nav.launch.py stack:=amcl map:=$HOME/m_map.yaml

# nav stack already running elsewhere: web parts only
ros2 launch robot_web_nav web_nav.launch.py stack:=none

  3. Open the page

    Go to http://<robot-pc-ip>:8000. The page connects to the websocket on the same host by itself. To use another address, add ?ws=ws://host:port to the page URL.

When the pills turn red

  • no rosbridge / disconnected: the web launch isn't running, rosbridge isn't installed, or port 9090 is blocked. The page retries every 2 s.
  • Nav2 not running: no navigate_to_pose server. Start a stack, or check its log.
  • web_nav_bridge silent: the helper node has stopped. Restart the web launch.
  • no map: nothing is publishing /map yet.

Test status (11 Oct 2026)

web_nav_bridge was tested against a stand-in for Nav2: reporting Nav2 not running, the robot pose, feedback while driving, arrival, cancel, and a goal replaced mid-drive. The page loads in a browser. The map drawing and clicking to set goals still need a live check once rosbridge is installed.

(10)Android app

Robot Nav, a native app for the same websocket

Robot Nav is a native Android app written in Kotlin. It connects straight to rosbridge and uses the same topics as the web page, so nothing changes on the robot side: start web_nav.launch.py with either stack, and the app and browser can be used side by side.

The app draws the map itself, so pinch-zoom and dragging a heading feel native. The phone remembers the robot's address and your saved spots, and keeps the screen on while you navigate.

package com.hoverboard.robotnav Android 8.0+ (API 26) APK ~1 MB one dependency OkHttp 4.12

  1. Start the robot side

    This is the same launch as for web navigation, and it needs ros-humble-rosbridge-suite installed.

    robot PC
    ros2 launch robot_web_nav web_nav.launch.py stack:=cartographer map:=$HOME/m_map.pbstream
# or: stack:=amcl map:=$HOME/m_map.yaml

  2. Install the APK

    The built APK is ~/RobotNav.apk. Copy it to the phone and open it, allowing "install unknown apps". Or install it over USB with USB debugging turned on:

    robot PC
    ~/Android/Sdk/platform-tools/adb install -r ~/RobotNav.apk

  3. Connect

    Tap Robot address and enter ws://<robot-pc-ip>:9090. The default is ws://192.168.1.12:9090. The phone must be on the same Wi-Fi. If ufw is enabled, open port 9090/tcp. The app retries every 2 s whenever the connection drops.

Inside the app

  • RosBridge.kt is the rosbridge v2 client over an OkHttp websocket. It re-subscribes after every reconnect and advertises a topic before its first publish.
  • MapView.kt draws the occupancy grid, robot, plan and goal, and handles the touch gestures.
  • MainActivity.kt handles the topics, status panel, robot address and saved spots. It decodes /map off the UI thread.

Test status (11 Oct 2026)

The app builds cleanly, the APK is signed with the debug key, and its manifest is checked (API 26–34, internet permission, launcher entry). It hasn't run on a phone or against a live rosbridge yet.

Rebuild on the robot PC
