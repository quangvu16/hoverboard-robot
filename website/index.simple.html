A hoverboard turned into an
autonomous ROS 2 robot

The robot uses a hoverboard's hub motors and FOC mainboard as its drive base. An ESP32 links it to a ROS 2 Humble PC over Wi-Fi. A 360° LiDAR, an IMU and three ultrasonic sensors feed Cartographer mapping and Nav2 navigation. You can drive it from a browser or an Android app.

ROS 2 Humble ESP32 LDROBOT LD14 LiDAR MPU9250 IMU Cartographer Nav2 robot_localization EKF

What it does

One bringup launch starts the base, the LiDAR and the robot model. Everything else layers on top of it.

Mapping

Cartographer (or slam_toolbox) builds a 2D map from the LiDAR. Save it as .pbstream plus .yaml/.pgm.

Navigation

Nav2 plans and follows paths on a saved map. It can localize with Cartographer or AMCL, or navigate while it maps.

Sensor fusion

An EKF fuses wheel odometry with the MPU9250 gyro and publishes /odom/filtered for Nav2 and Cartographer.

Web control

A page served over rosbridge shows the map and the robot. Click to set a goal, cancel it, set the pose, or save spots.

Android app

A Kotlin app uses the same topics as the web page, so you can navigate from a phone.

Safety reflexes

Firmware on the ESP32 reverses at 350 mm (front sonar) and turns away at 50 mm (side sonars). Turn and stop LEDs follow the motion.

Exploration & coverage

Two frontier explorers (explore_lite, auto_mapper) and a Spiral-STC full-coverage planner.

Manual driving

Drive by gamepad, keyboard teleop or rqt_robot_steering. Laser follow, avoid and warning behaviours are also included.

Architecture

The base controller is not a ROS node. The ESP32 speaks small binary UDP protocols, and one bridge node translates them into standard ROS topics and TF.

LiDAR over UDP

"LDS1" datagrams carry little-endian millimetre ranges. The scan is mirrored with a negative angle_increment, so the data is never reordered.

Telemetry & commands

HBT1 packets carry wheel ticks, sonar, light state and IMU data. HBC1 packets carry wheel RPM commands. The ESP32 works in RPM and ticks; the ROS side converts to metres.

One source of geometry

Wheel radius, separation and speed limits are set only in hoverboard_base.yaml. Bridge topics are relative names, so you can run several robots in separate namespaces.

Get started

On a ROS 2 Humble machine with rmw_cyclonedds_cpp. Run one navigation stack at a time.

Build

cd ~/robot_ws && colcon build
source ~/robot_ws/install/local_setup.bash

Bring up the robot

ros2 launch robot_bringup robot_bringup.launch.py        # base + LiDAR + EKF + URDF

Build a map and save it

ros2 launch robot_cartographer cartographer_nav.launch.py
ros2 run robot_cartographer save_map ~/m_map

Navigate on the saved map

ros2 launch robot_cartographer cartographer_nav.launch.py map:=$HOME/m_map.pbstream

Or drive it from a browser

sudo apt install ros-humble-rosbridge-suite
ros2 launch robot_web_nav web_nav.launch.py stack:=cartographer map:=$HOME/m_map.pbstream
# open http://<robot-pc-ip>:8000

Project status

Work in progress. The software stack is complete, but the robot is still being calibrated on real hardware:
  • wheel_separation_m (0.18 m) is not verified yet. It will be calibrated once the LiDAR is mounted on the chassis.
  • The IMU pose in the URDF is a placeholder until the board is mounted.
  • No camera is fitted yet. The vision and mediapipe packages have only been tested on recorded video.
Built with ROS 2 Humble, Cartographer, Nav2, robot_localization and rosbridge. Drive-base packages are ported from the Yahboom ROS 2 stack.
